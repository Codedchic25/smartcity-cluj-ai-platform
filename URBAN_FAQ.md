# 🏙️ Technical & Operational Frequently Asked Questions: Smart City Cluj IoT Core

This document addresses the most common architectural, security, and data management questions regarding the urban control platform.

---

### Q1: Why do the charts in the Streamlit dashboard continue to update smoothly, and why has the terminal stopped showing layout deprecation warnings?
* **Answer**: In earlier Streamlit versions, certain sizing properties could trigger deprecation warnings during auto-refresh cycles. We globally replaced those legacy syntaxes with native, stable layout parameters (such as fluid container layouts and explicit `use_container_width=True` flags) across all active pages (`Dashboard`, `Settings`, `Analytics`), ensuring responsive viewport scaling with zero console warnings.

### Q2: How does the simulator guarantee data isolation and 100% offline execution inside containerized environments?
* **Answer**: The platform enforces defensive global state initialization directly inside `main.py`, completely eliminating network or external cloud API dependencies for storage, threshold management, and local alerting. The system directly queries the central `DATABASE_PATH` database managed transactionally through the `CityRepository` class. All cross-page navigation `KeyError` regressions are completely neutralized via structured checks on `st.session_state`.

### Q3: What happens to city monitoring if the external connection to the LLM cloud provider (Groq) experiences an outage or network error?
* **Answer**: The system implements a robust **Fail-Safe** framework across all AI modules. Every API call to the inference model is encapsulated inside defensive `try/except` blocks. If the external network drops, the system intercepts the exception, logs it to the console via `LOGGER.error`, and renders a controlled informational message in the UI without halting the rest of the platform. IoT sensor ingestion into SQLite, live Plotly chart rendering, database updates, and 10-second cooldown alert logging into `security_alerts.log` continue operating 100% uninterrupted and locally isolated.

### Q4: How does the context-aware pipeline deliver high-precision AI recommendations without overloading the model's context window?
* **Answer**: Instead of sending the entire massive telemetry history to the assistant (which would introduce high latency and unnecessary token overhead), the dedicated context collector inside `TelemetryContextReader` performs a secure file-stream read to extract strictly the latest 5 lines from the physical `security_alerts.log` audit file. This compact snippet is dynamically injected into the core prompt template from `ai_tests/prompts.txt`. The model receives a dense, clean, and recent temporal snapshot, generating high-precision administrative recommendations directly via the production `openai/gpt-oss-20b` instance operated by `GroqProvider`.

### Q5: How does the application protect operator session data (`st.session_state`) against Session Cross-Talk attacks in a multi-user cloud environment?
* **Answer**: The Streamlit runtime spins up a completely isolated execution context for every browser tab opened by a new user. All variables stored inside `st.session_state` (such as the `authenticated` flag, active language selection, or response history generated by `openai/gpt-oss-20b`) reside in a dedicated, thread-isolated memory container bound exclusively to that execution session. There is zero risk of one cloud operator accessing another operator's session state, guaranteeing strict data privacy and isolation per individual session.
